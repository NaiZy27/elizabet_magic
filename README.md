# Elizabet Magic

Приём и ведение заказов на подарочные боксы: клиентский Telegram-бот, веб-админка
и фоновые задачи.

Путь клиента: соцсеть → ссылка «Заказать бокс» → бот → боксы (у каждого свои ложечки,
видео, цвета и пожелания) → город и пункт выдачи → получатель и email для чека →
оплата → номер заказа и чек → заказ в панели → сборка → смена статусов →
уведомления клиенту → трек-номер → пункт выдачи → получение.

Постоянному клиенту пункт выдачи и контакты подставляются из прошлого заказа.

## Требования

- Python 3.12 (ровно 3.12: на этой версии собирается окружение в контейнерах)
- Poetry 2.x — версия должна совпадать с той, что стоит в образе, иначе `poetry.lock` не прочитается
- Docker с плагином Compose
- Postgres 16 и Redis 7 поднимаются контейнерами, отдельно ставить не нужно

## Первый запуск

```bash
cp .env.example .env         # заполнить BOT_TOKEN, BOT_USERNAME, пароль базы
poetry install --with dev    # локальное окружение: ruff, pytest, автодополнение в IDE
make up                      # postgres, redis, web, bot, worker, scheduler
make migrate                 # создать схему
make seed-demo               # каталог, цвета, тексты + тестовые пункты выдачи
make admin u=elizabet        # логин владелицы, пароль спросит интерактивно
```

Сборщиков владелица заводит сама в панели, в разделе «Пользователи». Сборщик видит
доску, состав и пожелания, меняет этапы и пишет заметки; деньги, клиенты, чеки,
каталог и настройки ему недоступны.

Админка — `http://localhost:8000/admin`, бот работает поллингом и никакого домена
для разработки не требует.

`make seed-demo` отличается от `make seed` только тестовыми пунктами выдачи: без них
шаг доставки в боте упрётся в пустой справочник, пока не подключена служба доставки.

## Чего пока нет

- **Ссылки на чеки Робочеков.** Робокасса не отдаёт их по API: чек уходит клиенту
  на email, а в панели он «Передан в Робочеки». Ссылку можно вставить в карточке
  заказа из истории чеков Робочеков — тогда она придёт клиенту и в бот.

## Пароли от панели

Свой пароль каждый меняет сам: значок ключа рядом с логином в меню панели
(`/admin/password`) — текущий пароль, новый (от 12 символов) и повтор. После смены
пароля все остальные входы под этим логином закрываются (на других устройствах
придётся войти заново); то же — когда владелица задаёт новый пароль сборщику в
«Настройки → Доступ». Неверный текущий пароль считается в те же 5 попыток, что и вход.

## Повседневные команды

| Команда | Что делает |
|---|---|
| `make up` / `make down` | поднять / остановить всё |
| `make logs` | логи всех контейнеров |
| `make migrate` | применить миграции |
| `make revision m="что поменяли"` | создать миграцию по изменениям в моделях |
| `make seed` / `make seed-demo` | стартовые данные (и тестовые ПВЗ) |
| `make test` | тесты |
| `make lint` / `make fmt` | проверка и форматирование (ruff) |
| `make psql` | консоль базы |
| `make backup` | дамп базы |

## Как устроен репозиторий

```
src/core/      общее: модели, сервисы, интеграции
    models/    схема БД (SQLAlchemy 2.0)
    services/  вся бизнес-логика — цены, заказы, очередь, оплата, доставка
    workdays.py расчёт дат готовности: чистые функции, без базы
src/bot/       клиентский Telegram-бот (aiogram)
src/web/       FastAPI: админка, вебхуки, страница оплаты
src/worker/    фоновые задачи (Taskiq)
migrations/    Alembic
tests/         тесты
admin_web_panel_demo/  демо-разметка админки на Django-шаблонах — образец вёрстки
```

Правила, которых держимся: деньги — целые копейки, время в базе — UTC с таймзоной,
схема меняется только миграциями, бизнес-логика живёт в `core/services`.

## Проверка схемы после клонирования

Первая миграция написана вручную. Убедиться, что она совпадает с моделями:

```bash
make migrate
docker compose run --rm web alembic revision --autogenerate -m "sanity check"
```

Сгенерированная миграция должна получиться пустой (`pass` в `upgrade`). Если в ней
что-то есть — расхождение между моделями и миграцией, файл нужно удалить и починить
первую миграцию. Это единственная разовая проверка, дальше миграции создаются обычным
`make revision`.

## Сервер

Разворачивается на Ubuntu тем же `docker compose`, снаружи — nginx с сертификатом
от certbot. Наружу опубликован только `web` на `127.0.0.1:8000`, бот работает
поллингом и домена не требует.

```bash
git clone https://github.com/NaiZy27/elizabet_magic.git /opt/elizabet-magic
cd /opt/elizabet-magic
cp .env.example .env            # заполнить, см. ниже
docker compose up -d --build
docker compose run --rm web alembic upgrade head
docker compose run --rm web python -m core.seed
docker compose run --rm web python -m web.create_admin elizabet
```

Обязательное в `.env` сервера:

| Переменная | Значение |
|---|---|
| `ENVIRONMENT` | `production` |
| `COMPOSE_FILE` | `docker-compose.yml` — иначе подхватится `docker-compose.override.yml` для разработки |
| `DATABASE_URL` / `REDIS_URL` | хосты `postgres` и `redis` (имена контейнеров) |
| `PUBLIC_BASE_URL` | `https://домен` — отсюда берётся ссылка на оплату |
| `ADMIN_BASE_URL` | `https://crm.домен` — отсюда ссылки на заказы в сообщениях владелице |
| `ADMIN_HTTPS_ONLY` | `true` |
| `ADMIN_SESSION_SECRET` | длинная случайная строка |
| `PAYMENTS_MODE` | `stub` на тестовом контуре, `robokassa` — когда подключим приём денег |

С `PAYMENTS_MODE=stub` ключи Робокассы не нужны, но оплата не настоящая: кнопка на
странице оплаты просто отмечает заказ оплаченным. Каждый процесс пишет об этом
предупреждение в лог при старте.

Конфиги nginx собираются под свои домены:

```bash
./deploy/render-nginx.sh домен crm.домен     # готовые файлы — в deploy/nginx/out/
```

Обновление на сервере:

```bash
git pull && docker compose up -d --build
docker compose run --rm web alembic upgrade head
```

## Бэкапы

[deploy/backup.sh](deploy/backup.sh) снимает дамп базы, кладёт его в
`/var/backups/elizabet-magic` (хранение 14 дней) и отправляет копию файлом в Telegram —
на том же диске копия пропала бы вместе с сервером. Куда слать, задаёт `BACKUP_CHAT_ID`,
по умолчанию — чат владелицы (`OWNER_CHAT_ID`); чат сборщика не используется: в дампе
персональные данные покупателей. `BACKUP_CHAT_ID=0` выключает отправку,
`BACKUP_PASSPHRASE` шифрует файл перед отправкой. Если бэкап не получился, в тот же
чат приходит «⚠️ Бэкап базы … не получился» — о сломанных копиях узнаём сразу.

Проверить, что всё работает:

```bash
crontab -l | grep backup                    # задача стоит в расписании
tail -n 20 /var/log/em-backup.log           # как прошли последние запуски
ls -lh /var/backups/elizabet-magic          # копии на диске
./deploy/backup.sh                          # запуск вручную — файл должен прийти в чат
```

```bash
crontab -e
# 0 3 * * * cd /opt/elizabet-magic && ./deploy/backup.sh >> /var/log/em-backup.log 2>&1
```

Восстановление из копии:

```bash
# если файл зашифрован
openssl enc -d -aes-256-cbc -pbkdf2 -in em-2026-09-24.sql.gz.enc -out em.sql.gz

docker compose stop web bot worker scheduler
gunzip -c em.sql.gz | docker compose exec -T postgres psql -U em -d elizabet_magic
docker compose start web bot worker scheduler
```

Раз в пару месяцев стоит проверять, что копия действительно разворачивается: бэкап,
который никто не пробовал восстановить, — это ещё не бэкап.

## Робокасса

`PAYMENTS_MODE=robokassa`, в `.env` — `ROBOKASSA_LOGIN`, `ROBOKASSA_PASSWORD1`,
`ROBOKASSA_PASSWORD2`, `ROBOKASSA_HASH_ALGO` (как в кабинете), `ROBOKASSA_IS_TEST`.

В кабинете магазина, «Технические настройки»:

| Поле | Значение | Метод |
|---|---|---|
| Result URL | `https://домен/webhooks/robokassa/result` | POST |
| Success URL | `https://домен/pay/robokassa/success` | GET |
| Fail URL | `https://домен/pay/robokassa/fail` | GET |

Кнопка «Оплатить» ведёт на `/pay/<токен>/go`: страница сама отправляет в Робокассу
POST-форму с чеком — бокс, каждая услуга и доставка отдельными строками, `tax: none`
для Робочеков СМЗ. Именно форма, а не ссылка: чек с парой боксов занимает тысячи
символов. Логика — `core/services/robokassa.py`.

**Тестовый режим.** У Робокассы для него отдельные пароли №1 и №2 (блок «Параметры
проведения тестовых платежей» в технических настройках). Пока `ROBOKASSA_IS_TEST=true`,
в `ROBOKASSA_PASSWORD1/2` должны стоять **тестовые** пароли; при переходе в бой —
боевые пароли и `ROBOKASSA_IS_TEST=false`, затем `docker compose up -d`. Счета,
выставленные в тестовом режиме, после переключения перевыставляются сами.

**Чеки.** Робочеки СМЗ подключаются в кабинете Робокассы и в «Мой налог»
(«Партнёры» → разрешение для Робокассы). Дальше чек на каждую оплату они пробивают
сами и шлют клиенту на email; в панели такой чек — «Передан в Робочеки». Если сумма
строк чека не сошлась с оплатой (заказ поправили руками), чек в кассу не уходит —
владелице придёт сообщение пробить его вручную.

**Сверка.** Раз в 10 минут воркер спрашивает Робокассу (OpStateExt) о счетах, по
которым клиент уходил в кассу за последние 3 дня, но оплата у нас не отмечена. Так
оплата не теряется, если уведомление на Result URL не дошло; владелице придёт
сообщение — частые такие сообщения значат, что Result URL настроен неверно.
В тестовом режиме (`ROBOKASSA_IS_TEST=true`) сверка выключена: OpStateExt не видит
тестовых оплат.

**Возвратов в системе нет.** Клиент пишет через «📞 Связаться с нами», владелица
возвращает деньги в кабинете Робокассы, аннулирует чек в «Мой налог» и отменяет
заказ в панели («Сроки и отмена» → «Отменить»).

**Проверка настоящими деньгами.** `PAYMENTS_TEST_AMOUNT_KOPECKS=100` в `.env` (вместе
с боевыми паролями и `ROBOKASSA_IS_TEST=false`): каждая строка чека стоит 1 ₽ —
«бокс + видео + доставка» оплачивается 3 ₽ настоящим построчным чеком Робочеков.
После проверки строку удалить и перезапустить контейнеры — иначе клиенты будут
платить по 1 ₽.

## Очистка тестовых данных

Перед запуском — удалить тестовых покупателей и заказы:

```bash
./deploy/backup.sh                                          # сначала бэкап
docker compose exec web python -m core.cleanup              # что будет удалено
docker compose exec web python -m core.cleanup --apply      # удалить
```

Заказы с настоящим чеком (оплата в боевом режиме) остаются целиком — чеки храним
по закону. Каталог, настройки, тексты, службы, пункты и логины панели не трогаются.

## Доставка

Службы — СДЭК, Яндекс Доставка, Ozon — **ручные**: отправку владелица оформляет сама
в приложении службы. Включаются в панели, раздел «Доставка»; клиенту показываются
пункты только включённых служб.

**Цены.** У каждой службы две цены, обе задаются в панели: **по Москве** (пункт выдачи
в Москве) и **по России** (все остальные пункты). Клиент видит цены служб в шаге
доставки и в разделе «Доставка» бота; цена выбранного пункта входит в итог и в чек.

**Данные для отправки.** При оплате владелице приходит карточка заказа с блоком
доставки, а на «Готов» — сообщение со всем для отправки: служба, адрес и код пункта,
получатель и телефон (тапом копируются), Telegram покупателя для связи (@ник или
ссылка на профиль, если ника нет), состав заказа. Этапы «Передан в доставку»,
«Доставлен в ПВЗ» и «Получен» она ставит сама.

**Адрес вручную.** Если клиент не нашёл свой пункт в списке, кнопка «✍️ Ввести адрес
пункта вручную» спрашивает службу, «в Москве или в другом городе» (от этого цена) и
адрес текстом. Владелица получает адрес как есть с пометкой «адрес клиент ввёл сам».

**Пункты выдачи** всех служб обновляются сами каждый понедельник ночью из открытых
источников, без ключей:

| Служба | Источник | Что берём |
|---|---|---|
| СДЭК | публичный список офисов СДЭК (`integration.cdek.ru/pvzlist`) | собственные офисы СДЭК в России, без постаматов и партнёрских пунктов |
| Яндекс | источник виджета выбора ПВЗ Яндекса | пункты Маркета и 5Post, без постаматов и закрывающихся в ближайшие 2 недели |
| Ozon | OpenStreetMap (Overpass API) | пункты с brand=Ozon; адрес — у дома, в котором стоит пункт |

Пропавшие из источника пункты выключаются; если источник отдал меньше половины
известных пунктов — ничего не выключается, а ошибка видна в разделе «Доставка».
Пункты Ozon в OpenStreetMap отмечают волонтёры: в Москве и больших городах покрытие
почти полное, в малых — не все пункты; адрес владелица сверяет в приложении Ozon.
Пункты Ozon грузятся дольше всех — Overpass опрашивается по 85 регионам, и публичные
серверы бывают перегружены, поэтому загрузка может занять пару часов. Если какой-то
регион так и не ответил, остальные всё равно обновятся, а пункты этого региона
останутся как были (в разделе «Доставка» будет видно, какие регионы не прочитались).
Вручную:

```bash
docker compose exec worker python -m core.services.pickup_sync cdek yandex ozon
```

## Очередь и дневной лимит

Даты готовности считаются по дневному лимиту из «Настроек → Рабочие дни»: по умолчанию
2 бокса с видео или 4 без видео в день (можно смешивать: 1 с видео + 2 без). Клиент видит
место в очереди и дату ещё до оплаты, в итоге заказа.

## Связаться с нами

Сообщение клиента из «📞 Связаться с нами» бот пересылает владелице (`OWNER_CHAT_ID`)
вместе со ссылкой на профиль клиента и номером последнего заказа. Ответить можно,
написав клиенту напрямую по этой ссылке.
