# Elizabet Magic

Приём и ведение заказов на подарочные боксы: клиентский Telegram-бот, веб-админка
и фоновые задачи.

Путь клиента: соцсеть → ссылка «Заказать бокс» → бот → боксы (у каждого свои ложечки,
видео, цвета и пожелания) → город и пункт выдачи → получатель и email для чека →
оплата → номер заказа и чек → заказ в панели → сборка → смена статусов →
уведомления клиенту → трек-номер → пункт выдачи → получение.

Постоянному клиенту пункт выдачи и контакты подставляются из прошлого заказа.

## Требования

- Python 3.12 (ровно 3.12: на этой версии собирается окружение в контейнерах)
- Poetry 2.x — версия должна совпадать с той, что стоит в образе, иначе `poetry.lock` не прочитается
- Docker с плагином Compose
- Postgres 16 и Redis 7 поднимаются контейнерами, отдельно ставить не нужно

## Первый запуск

```bash
cp .env.example .env         # заполнить BOT_TOKEN, BOT_USERNAME, пароль базы
poetry install --with dev    # локальное окружение: ruff, pytest, автодополнение в IDE
make up                      # postgres, redis, web, bot, worker, scheduler
make migrate                 # создать схему
make seed-demo               # каталог, цвета, тексты + тестовые пункты выдачи
make admin u=elizabet        # логин владелицы, пароль спросит интерактивно
```

Сборщиков владелица заводит сама в панели, в разделе «Пользователи». Сборщик видит
доску, состав и пожелания, меняет этапы и пишет заметки; деньги, клиенты, чеки,
каталог и настройки ему недоступны.

Админка — `http://localhost:8000/admin`, бот работает поллингом и никакого домена
для разработки не требует.

`make seed-demo` отличается от `make seed` только тестовыми пунктами выдачи: без них
шаг доставки в боте упрётся в пустой справочник, пока не подключена служба доставки.

## Чего пока нет

- **Возвраты через API Робокассы.** Оплата идёт через Робокассу (см. «Робокасса» ниже),
  а возврат владелица делает в кабинете Робокассы; кнопка «Оформить возврат» в панели
  фиксирует это, аннулирует чек и отменяет заказ.
- **Службы доставки.** СДЭК и Яндекс не подключены: нет договора. Пункты выдачи
  берутся из кэша в базе, стоимость — резервная цена из раздела «Доставка».
- **Отправления и трек-номера.** Появятся вместе со службой доставки. Пока прибытие
  в пункт выдачи отмечается кнопкой «Прибыл в ПВЗ» в карточке заказа.
- **Чеки НПД.** Хранятся в таблице `receipts`. С заглушкой оплаты заводится тестовый
  чек; при ручной работе ссылку на чек из «Мой налог» вставляют в карточке заказа.
  Регистрация через Робочеки придёт вместе с Робокассой.

## Повседневные команды

| Команда | Что делает |
|---|---|
| `make up` / `make down` | поднять / остановить всё |
| `make logs` | логи всех контейнеров |
| `make migrate` | применить миграции |
| `make revision m="что поменяли"` | создать миграцию по изменениям в моделях |
| `make seed` / `make seed-demo` | стартовые данные (и тестовые ПВЗ) |
| `make test` | тесты |
| `make lint` / `make fmt` | проверка и форматирование (ruff) |
| `make psql` | консоль базы |
| `make backup` | дамп базы |

## Как устроен репозиторий

```
src/core/      общее: модели, сервисы, интеграции
    models/    схема БД (SQLAlchemy 2.0)
    services/  вся бизнес-логика — цены, заказы, очередь, оплата, доставка
    workdays.py расчёт дат готовности: чистые функции, без базы
src/bot/       клиентский Telegram-бот (aiogram)
src/web/       FastAPI: админка, вебхуки, страница оплаты
src/worker/    фоновые задачи (Taskiq)
migrations/    Alembic
tests/         тесты
admin_web_panel_demo/  демо-разметка админки на Django-шаблонах — образец вёрстки
```

Правила, которых держимся: деньги — целые копейки, время в базе — UTC с таймзоной,
схема меняется только миграциями, бизнес-логика живёт в `core/services`.

## Проверка схемы после клонирования

Первая миграция написана вручную. Убедиться, что она совпадает с моделями:

```bash
make migrate
docker compose run --rm web alembic revision --autogenerate -m "sanity check"
```

Сгенерированная миграция должна получиться пустой (`pass` в `upgrade`). Если в ней
что-то есть — расхождение между моделями и миграцией, файл нужно удалить и починить
первую миграцию. Это единственная разовая проверка, дальше миграции создаются обычным
`make revision`.

## Сервер

Разворачивается на Ubuntu тем же `docker compose`, снаружи — nginx с сертификатом
от certbot. Наружу опубликован только `web` на `127.0.0.1:8000`, бот работает
поллингом и домена не требует.

```bash
git clone https://github.com/NaiZy27/elizabet_magic.git /opt/elizabet-magic
cd /opt/elizabet-magic
cp .env.example .env            # заполнить, см. ниже
docker compose up -d --build
docker compose run --rm web alembic upgrade head
docker compose run --rm web python -m core.seed
docker compose run --rm web python -m web.create_admin elizabet
```

Обязательное в `.env` сервера:

| Переменная | Значение |
|---|---|
| `ENVIRONMENT` | `production` |
| `COMPOSE_FILE` | `docker-compose.yml` — иначе подхватится `docker-compose.override.yml` для разработки |
| `DATABASE_URL` / `REDIS_URL` | хосты `postgres` и `redis` (имена контейнеров) |
| `PUBLIC_BASE_URL` | `https://домен` — отсюда берётся ссылка на оплату |
| `ADMIN_BASE_URL` | `https://crm.домен` — отсюда ссылки на заказы в сообщениях владелице |
| `ADMIN_HTTPS_ONLY` | `true` |
| `ADMIN_SESSION_SECRET` | длинная случайная строка |
| `PAYMENTS_MODE` | `stub` на тестовом контуре, `robokassa` — когда подключим приём денег |

С `PAYMENTS_MODE=stub` ключи Робокассы не нужны, но оплата не настоящая: кнопка на
странице оплаты просто отмечает заказ оплаченным. Каждый процесс пишет об этом
предупреждение в лог при старте.

Конфиги nginx собираются под свои домены:

```bash
./deploy/render-nginx.sh домен crm.домен     # готовые файлы — в deploy/nginx/out/
```

Обновление на сервере:

```bash
git pull && docker compose up -d --build
docker compose run --rm web alembic upgrade head
```

## Бэкапы

[deploy/backup.sh](deploy/backup.sh) снимает дамп базы, кладёт его в
`/var/backups/elizabet-magic` (хранение 14 дней) и отправляет копию файлом в Telegram —
на том же диске копия пропала бы вместе с сервером. Куда слать, задаёт `BACKUP_CHAT_ID`
(по умолчанию служебный чат, иначе чат владелицы), `BACKUP_CHAT_ID=0` выключает отправку.
В дампе есть персональные данные покупателей, поэтому чат должен быть закрытым;
`BACKUP_PASSPHRASE` шифрует файл перед отправкой.

```bash
crontab -e
# 0 3 * * * cd /opt/elizabet-magic && ./deploy/backup.sh >> /var/log/em-backup.log 2>&1
```

Восстановление из копии:

```bash
# если файл зашифрован
openssl enc -d -aes-256-cbc -pbkdf2 -in em-2026-09-24.sql.gz.enc -out em.sql.gz

docker compose stop web bot worker scheduler
gunzip -c em.sql.gz | docker compose exec -T postgres psql -U em -d elizabet_magic
docker compose start web bot worker scheduler
```

Раз в пару месяцев стоит проверять, что копия действительно разворачивается: бэкап,
который никто не пробовал восстановить, — это ещё не бэкап.

## Робокасса

`PAYMENTS_MODE=robokassa`, в `.env` — `ROBOKASSA_LOGIN`, `ROBOKASSA_PASSWORD1`,
`ROBOKASSA_PASSWORD2`, `ROBOKASSA_HASH_ALGO` (как в кабинете), `ROBOKASSA_IS_TEST`.

В кабинете магазина, «Технические настройки»:

| Поле | Значение | Метод |
|---|---|---|
| Result URL | `https://домен/webhooks/robokassa/result` | POST |
| Success URL | `https://домен/pay/robokassa/success` | GET |
| Fail URL | `https://домен/pay/robokassa/fail` | GET |

В ссылку на оплату уходит чек: бокс, каждая услуга и доставка отдельными строками,
`tax: none` — для Робочеков СМЗ. Логика — `core/services/robokassa.py`.

## Очередь и дневной лимит

Даты готовности считаются по дневному лимиту из «Настроек → Рабочие дни»: по умолчанию
2 бокса с видео или 4 без видео в день (можно смешивать: 1 с видео + 2 без). Клиент видит
место в очереди и дату ещё до оплаты, в итоге заказа.

## Отзывы

Клиент оставляет отзыв кнопкой под сообщением «заказ получен» или в карточке заказа.
Владелица листает отзывы в боте («⭐ Отзывы») и публикует в канал кнопкой. Канал —
`REVIEWS_CHANNEL_ID`, бот должен быть в нём администратором.
